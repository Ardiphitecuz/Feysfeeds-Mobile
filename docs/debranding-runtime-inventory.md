that the mobile app is already independent of Folo.

### FeyFeeds sync contract and offline status

The current mobile + Worker contract is deliberately narrow and explicit: only the FeyFeeds-owned user namespace is treated as the source of truth for feed subscriptions, article timeline rows, read/bookmark state, and the supported account-level preferences/folder/list metadata. Feed data and local cache entries are namespaced by the active FeyFeeds user ID; the `last-user` marker restores only that account's saved state and the signed-out account's outbox remains recoverable for later sign-in.

The sync contract currently covers:
- feed add/delete and OPML import
- article timeline reads via incremental `cursor` pagination
- read/bookmark state upserts for entries the authenticated user owns
- per-user cache snapshots for feeds, timeline rows, folder/list memberships, and user preferences
- durable per-account outbox replay with idempotent retries for no-op and already-removed server states

Conflict policy: local writes are queued with a stable client mutation ID and replayed in FIFO order per account. When the server rejects a duplicate follow for a URL already owned by the same user, the operation is treated as success; when a delete hits a missing resource, it is also treated as success. Entry-state writes are optimistic locally and replay in sequence; retry failures keep the queued mutation intact rather than discarding the user's change. Server-side cursor pagination is the source of truth for incremental sync; invalid or stale cursors fail closed, and the client shows the last cached data while keeping the server-side token invalidated until a fresh cursor is fetched.

The mobile app keeps a durable outbox plus cached feed/timeline data for offline reads. On foreground/app launch or network recovery, the queue is replayed; if retry fails due to a real validation/auth issue, the queue remains in place and the UI shows offline/error messaging instead of silently falling back to Folo. Logout clears the active session state and the visible feed/timeline data while preserving the signed-out account's namespaced cache/outbox for later reuse; account deletion removes that account's namespaced data after a successful server-side delete.

This is intentionally not a blanket claim that all legacy Folo data or every screen has been migrated. The broader app still uses Folo-owned identities for non-FeyFeeds flows, and the migration remains a staged cutover rather than a full app-wide account replacement.

## Migration and release gates

Queued read/bookmark updates carry absolute boolean values and replay in order,
so the last successful mutation wins. Add conflicts are acknowledged only when
the same FeyFeeds account already follows that URL; repeated deletes are
acknowledged when the feed is already absent.

1. Extend Worker APIs for account migration, profile/storage, and sync behaviors.
   Feed/session routes have account ownership checks; broader account migration
   is still incomplete.
2. Add a migration path that imports feed URLs from OPML. Existing SQLite data
   remains available locally; old read/bookmark history cannot be mapped to new
   Worker entry IDs until a stable ID mapping/import contract is implemented.
3. Connect Home and Subscriptions to the Worker and persist their cache/outbox in
   SQLite KV. Remaining work includes broader native reader integration and
   device-level acceptance testing.
4. Move primary authentication only after required data routes and an explicit
   Folo account migration strategy are ready. Cross-domain legacy cookie
   migration is removed because it sent a Folo cookie to another Folo API domain
   and does not migrate identity to FeyFeeds. Home and Subscriptions now use a
   dedicated FeyFeeds session; other app capabilities still use the Folo session.
5. Remove backend trial restrictions after replacing the primary Folo APIs,
   while retaining feed subscriptions. The mobile paid UI/IAP removal is
   complete, but backend entitlement behavior has not been verified.
6. Remove remaining Folo API calls, domains, and packages. Verify using a clean
   install and a network trace that normal app use produces no requests to Folo
   domains.

The Worker now stores FeyFeeds users and sessions in D1, hashes passwords with
Workers Web Crypto PBKDF2, stores only session-token digests, and rejects missing,
invalid, expired, or revoked sessions. Private data remains scoped to the
verified FeyFeeds user ID. Firebase Auth is no longer used by FeyFeeds Cloud.
The app-wide primary authentication has not switched to the FeyFeeds account
system. Home and Subscriptions use the FeyFeeds session independently; other
data operations still depend on Folo. Login attempt limits and account profile,
preferences, and deletion are available through the FeyFeeds account API.

### Account/login cutover blockers

- `apps/mobile/src/App.tsx` calls `usePrefetchSessionUser()` and redirects to
  the Folo login; `apps/mobile/src/lib/auth.ts` owns Better Auth cookie restore,
  sign-out, and query invalidation. Replacing only the visible login form would
  leave bootstrap and session state inconsistent.
- Login screen callers are `apps/mobile/src/modules/login/email.tsx` and
  `apps/mobile/src/modules/login/social.tsx`; they update `userSyncService`
  and the Follow user store. Main login is therefore intentionally not cut over.
- Main timeline selectors and screen actions use `@follow/store/user`;
  `apps/mobile/src/modules/settings/SettingsList.tsx`, `Account.tsx`,
  `EditProfile.tsx`, and `sync-queue.ts` use Folo identity for profile, settings,
  and queued updates. Reader, subscription/list, unread, action-rule, and other
  shared Follow stores/queries also expect the Folo user ID and `FollowClient`.
- FeyFeeds currently serves Home/Subscriptions data inside its dedicated cloud
  screen (`apps/mobile/src/modules/settings/routes/FeyFeedsCloud.tsx`), while
  `apps/mobile/src/modules/screen/TimelineSelectorProvider.tsx`,
  `apps/mobile/src/modules/entry-list/EntryListSelector.tsx`,
  `apps/mobile/src/modules/settings/SettingsList.tsx`,
  `apps/mobile/src/modules/settings/routes/Account.tsx`,
  `apps/mobile/src/modules/settings/routes/EditProfile.tsx`, and
  `apps/mobile/src/modules/settings/sync-queue.ts` still depend on Folo identity
  or endpoints. Main Folo-backed reader history, lists, profile/settings,
  unread and action operations have no FeyFeeds API contract or safe ID mapping.
- No authenticated Folo account export/link contract is available here. Do not
  auto-link by email. Existing Firebase UID accounts/data remain unmigrated;
  users can create a FeyFeeds account and use/import feed subscriptions through
  OPML. Imported feeds remain intact on the FeyFeeds account. Existing article
  read/bookmark history, list metadata, settings, and social/account links cannot
  yet be safely transferred.
- Email delivery is not configured. Password recovery and email verification
  are unavailable and are release blockers before password-based public launch.

Entry-state reads now join each state to its cached article and owning feed for
the authenticated user. Read/bookmark writes use one ownership-scoped D1
insert/upsert, so arbitrary or cross-account entry IDs cannot create or change
state. Missing and unowned entries share the same 404 response. Existing state
filters and the 100-row maximum remain unchanged.

### FeyFeeds feed fetch and parser status

The Worker refresh path supports RSS 2.0, Atom, and JSON Feed 1.0/1.1 with a
shared article model for source ID, title, safe HTTP(S) URL, HTML/text content,
summary, author, categories, enclosure/media attachments, and publication time.
Entry IDs retain the existing `rss_<sha256(feed id + GUID)>` scheme; GUID/JSON
Feed ID remains the upsert key. URL fallback is used only when the feed omits
an ID, and repeated IDs in one response are deduplicated. Migration 0007 adds
category and attachment JSON columns with defaults, preserving old rows and
entry-state IDs. XML is parsed with fast-xml-parser and JSON Feed with the
Workers JSON runtime. HTML is sanitized on write and timeline reads with a
whitelist; clients should still isolate untrusted feed content when rendering.

Refresh is bounded to 100 entries, 1.5 MB streamed response bodies, 12 seconds
per request, three redirects, 100 entries per feed, and five due feeds per
cron invocation. URLs/redirects reject unsafe schemes, credentials, unusual
ports, local names, IP literals, and non-public/reserved IPv4. Workers fetch
cannot pin DNS resolution to a validated IP, so DNS rebinding remains residual
risk and the validation does not guarantee the network destination is public.
RSS, Atom, and JSON Feed parsing is implemented. Website autodiscovery now
finds advertised feeds, and RSSHub routes can be resolved against an explicitly
configured public HTTPS self-hosted instance. The feed record stores the resolved
URL, which remains stable across refreshes and participates in per-user URL
uniqueness; entry IDs continue to derive from the FeyFeeds feed ID and source
GUID. RSSHub specialized routes can cover
some source-specific feeds, subject to the installed routes and source site.
There is no general search/trending catalog, no arbitrary article-page content
extraction, and no support for non-feed source APIs. Feed HTML is sanitized on
write and timeline read, but the app should still isolate rendered feed content.
These capabilities do not establish Folo feed parity.
